# Implementation decisions

October 6 pronunciation follow-up (FR-08): new submissions use `prepare-v3` with the immutable English `pronunciation-v2` profile and `literal-dictionary-v1` rules. Default number/acronym/date handling retains the legacy structural script. Optional digit/symbol, cardinal/decimal and scientific exponent reading, uppercase ASCII word spelling, and explicitly ordered Gregorian calendar dates produce an exact script before synthesis. Unsupported profile versions, enum values, languages and engines are refused; native settings explain their capability and offer a supported English reset. Dictionary rules remain case-sensitive whole-term substitutions in order, including cascades; replacements are protected from subsequent generic interpretation. Synthetic formatting cues cannot be mistaken for source numbers or acronyms.

Preparation carries UTF-16 source origins through markup removal, link captures, code-symbol verbalization and table-cell formatting. Review records raw source ranges and each step's before/after/rule in execution order; cascades may refer to the same raw range repeatedly. Invalid explicitly chosen dates are preserved and flagged. Dictionary content revision hashes named From/To fields, not default ValueTuple JSON. Bounds cover raw source, dictionary entries/lengths, final mapped script (2,000,000 characters), and review count/content (100,000 changes / 8,000,000 combined characters); cancellation is checked during transformation. Submission, review and audition capture profile/settings before asynchronous work. Queue admission and dispatch reject mismatched captured profile/dictionary revisions, and both provider adapters validate profile support before runtime or HTTP access while sending only the existing contract's exact script. Nullable profiles preserve the original six-field settings JSON fingerprint for legacy queued jobs and receipts. SQLite and offline backup/restore retain profile, review, script and receipt identity. Native controls compile; real pronunciation, visual/action/accessibility and both current speech engines remain separate acceptance.

Export staging now uses an exclusive Windows read/write/delete handle from creation or recovery through checksum validation and non-overwriting rename. A versioned receipt records the volume serial, 128-bit file ID and creation FILETIME; resumed incomplete bytes must also match the exact prefix of the locked, checksum-validated private MP3. Replacement files, same-file edits, extra bytes and unsupported identities are preserved. Legacy boolean ownership alone cannot authorize removing an incomplete file; an existing complete copy remains eligible through its finished-audio checksum. New receipts leave the legacy boolean false so older readers preserve incomplete staging they cannot verify. No queue-schema or synthesis-fingerprint change is needed. The implementation follows Microsoft's [file identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [basic file information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info), and [handle-based rename](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) contracts.

Graceful failure deletes a newly created partial only through its original held handle, including failed ownership persistence; resumed files remain for another attempt. A process loss between creation and its identity checkpoint leaves an unrecognized orphan for inspection. Explicit replacement-destination retry can preserve altered or locked old staging, clears its old publication receipt, and durably displays that preservation notice instead of requiring removal of an unverified file before the user can export elsewhere.

Managed MP3 removal hashes and deletes through one Windows handle opened for read/delete without sharing write or delete access. This closes the gap between a path-based checksum and a later path-based deletion. Exports use their frozen SHA-256 receipt without adding a new queue schema; installation receipts continue to require both length and checksum. A missing export is idempotent, while a changed file, invalid receipt or competing writer leaves removal incomplete for retry. The guarantee covers the finished MP3; the existing staging ownership/recovery rules and actual OneDrive acceptance remain separate work.

October 6 whole-library deletion follow-up: the prior native loop paused future dispatch but could remove an older item while a later selected worker still generated or published. A bulk operation now freezes the reviewed identities under the dispatch gate, stops and settles selected active work first, then atomically records all tombstones/export scopes and diagnostic events in one SQLite transaction before any narration removal. The JSON update preserves frozen content, original timestamps, ordering and settled publication receipts; it returns and verifies the effective recorded export-removal consent (including a same-process retry after lost acknowledgement) and uses the existing schema/flags so interrupted requests remain compatible with startup recovery. Failed items retain their individual identity/title/error and deletion state while other items finish. Lost transaction acknowledgement pauses before removal without assuming the requests were absent; recorded intents reconcile on relaunch. Deletion-checkpoint errors fence dispatch even if a caller toggles pause, and repaired deletion clears only its own outstanding checkpoint error. Submission, retry, queue ordering and cleanup cannot overlap the batch. Native removal runs off the UI thread, selection lookup is linear, deferred library refreshes read current state, and native confirmation rereads recorded requests, and the retry dialog explains pending source/export scopes, the retained current draft and that closing the dialog does not withdraw a recorded request. Automated races cover readiness settlement, publication before/after rename, true SQLite transaction abort, real Windows file locks, lost acknowledgement, scope changes, retry/submission/cleanup fencing and restart. Native one/all visual/action acceptance and actual bulk-deletion host termination remain open.
October 6 restore process-loss acceptance: optional recovery observers expose the durable incoming-retention, original-item-return and committed-state boundaries without changing normal recovery policy. The unshipped acceptance host is confined to isolated repository artifact folders, requires a fresh boundary marker and its own completed backup, and publishes an exclusive flushed marker bound to its live PID, operation, workspace and journal hash. It waits at most two minutes; the parent has a 60-second observation allowance and terminates only its retained child handle. Normal application and maintenance commands never request a barrier. The 23-case/30-termination harness proves file/record preservation and idempotent packaged recovery at these Windows process-loss boundaries, including a second termination during recovery. Synthetic two-second PCM is encoded and fully decoded before seeding; this is artifact preservation evidence, not speech fidelity. Native UI, abrupt machine power loss, sleep/wake and deployment/service interruption remain separate acceptance.

October 6 setup-cache cleanup follow-up: cache review verifies the installation/cache ownership and complete inventory of each known completed distribution, excludes the active editor/bootstrap, executing source and busy/uncertain copies, and keeps unknown/incomplete staging. Native review presents exact folder, package identities, counts and bytes with separate confirmation; the CLI requires a matching review fingerprint and explicit removal flag. Read-only review does not create usage leases. Cached desktop/maintenance hosts acquire an installation-bound package-use lease until exit; cached native setup binds to that installation and refuses editor/maintenance startup rather than falling through to default private data. Portable sources retain their original behavior. Process residency checks also preserve prior hosts which predate the use-lease protocol; inaccessible residency is treated as uncertain.

Cleanup reacquires private and installation exclusion, revalidates the reviewed scope and holds package-use leases before recording a bounded removal journal. The journal embeds the release inventory, recomputes its known package identity and requires the removal ledger to match that inventory; a valid JSON edit cannot add an unrelated file without invalidating this binding. Every target file in a package is opened with read/delete access and no sharing, and checked through that handle before the first file is removed. This uses the [CreateFile access/sharing contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea); it strengthens package admission against locks, replacements and new opens. Each deletion is marked through its already verified handle. Only recorded empty directories are removed. A pending cleanup validates original ownership/state, allows already removed recorded files, rejects altered/unrecorded entries and resumes remaining removal. Installation/launch fencing and native review include this journal. Cache ownership and zero-byte use coordination records remain; distribution space is reclaimed without deleting private narration or exports. Actual host termination, power loss, legacy native UI loading races and fresh-machine acceptance require separate evidence.

October 6 Windows integration follow-up: a sealed optional `app/windows-integration.json` declaration requests per-user registration. Older packages retain their prior behavior; rollback retains an already installed setup-capable launcher and integration. The installation owns one HKCU uninstall key and two Start Menu links under its random installation identity. DisplayVersion follows the active release; UninstallString/ModifyPath invoke the stable launcher with --setup, preserving review and data-scope confirmation. No publisher identity or signing approval is invented. Shortcuts use the [Windows Script Host shortcut API](https://learn.microsoft.com/en-us/troubleshoot/windows-client/admin-development/create-desktop-shortcut-with-wsh) on a dedicated STA thread with a bounded wait; target, arguments and working directory are separate properties. Registry value names/types follow the [Windows uninstall metadata convention](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key) in the current user's hive; this custom application is not an MSI product.

A bounded ownership receipt and old/new journal bind exact shortcut checksums and generated registry values. Recovery checks every target/stage before deletion and each registry value before mutation, resumes partial value writes/link promotions, and refuses changed/unowned entries. The core pointer journal remains until integration settles; normal launch is fenced while pending. Uninstall verifies integration before committing intent and removes it before target binaries. Unknown shortcut-folder files survive, unknown registry values/subkeys stop removal, and missing owned entries are repairable. Native review fingerprints now include integration and its recovery journal. Windows registry writes are per-value operations rather than a transaction: external concurrent modification may leave a pending repair instead of an atomic update. Stages created before their ownership checkpoint remain for inspection. Eighteen tests exercise actual isolated HKCU entries and COM-authored/read links, initial installation/legacy rollback, registration/removal interruptions, changed recovery inputs, native consent invalidation, repair and preservation. No Windows Settings UI or real shortcut child launch is claimed by those checks.

October 6 stable-launcher follow-up: installation now copies an inventoried, self-contained single-file host to a stable root name and records its length/SHA256, owning installation and source package. Replacement stages and verifies the next image before a bounded journal. Same-handle checked removal of the old image, nonoverwriting promotion, ownership commit and stage cleanup are individually recoverable. The desktop pointer and launcher journals fence ordinary launch until settlement; a setup plan may validate a recorded old/new launcher or its verified stage without implicitly recovering. Changed records/images/stages remain for inspection. A normal plan verifies the active package and private schema; maintenance permits private-state repair while retaining binary/binding checks. Every plan holds the private lease and the actual host holds/releases the compatibility mutex on its owning thread before launching the child.

Setup copies the entire verified setup-capable release into an installation-owned sibling cache, revalidates its inventory, and passes typed --setup/--install-root arguments to that external desktop host. Older editor-only rollback retains the newer setup-capable kit. A previously verified cache supports recovery after committed uninstall has begun deleting source releases. Uninstall journals the separately owned root launcher and deletes it through its recorded Windows handle. The external setup cache remains retained after uninstall so an executing or interrupted setup is not swept; scoped cleanup is still required release work. Windows shortcut/uninstall registration follows this stable entry-point foundation. The single-file host bundles native libraries under the [.NET single-file deployment model](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview); .NET owns its runtime extraction cache, which is separate from narration state. Fault fixtures and plan inspection do not establish actual child UI startup, Windows registration or fresh-machine acceptance.

The actual Windows host uses the statically linked CLR superhost described by the [.NET single-file implementation announcement](https://devblogs.microsoft.com/dotnet/announcing-net-6-preview-1/). An initial inspection incorrectly required a separate coreclr.dll module and was corrected. Inspect now distinguishes that static layout from an extracted CLR under a caller-controlled bundle base or an external/unclassified runtime. Acceptance checks execute the single installed root file with absent external-runtime hints and a fixture extraction folder. This is host-layout evidence in the development environment; fresh-user/machine and servicing acceptance remain separate.

October 6 restore-lock follow-up: restore and rollback recovery now retry only Windows access/sharing/lock violations over a bounded 50–800 ms backoff. Every attempt rechecks managed-path guards and refuses an existing destination. Transient directory locks may settle; persistent locks fail with the restore journal and original state retained. Real Windows open-file fixtures exercise completion after release and exact original queue/artifact recovery after an unreleased lock. This addresses an observed incoming-jobs directory move denial during deployment regression; it does not establish abrupt host-crash or actual disk-full acceptance.

October 6 native deployment follow-up: a dedicated WPF setup mode reuses the verified installer transactions and owns the editor's compatibility mutex without loading the queue coordinator or speech provider. Review/check actions do not create either root. A single-use review binds package identity, installation owner/state, the exact pending journal hash and a bounded private inventory; apply reacquires the private lease and rechecks each before mutation. Explicit uninstall repeats the reviewed private fingerprint check immediately before its removal journal. Pending deployment is reviewed without implicit recovery. Install validates the saved queue before activation and never resets corrupt data. Launch releases setup before starting the verified active desktop. Uninstall refuses a source kit inside the installation root; a complete external portable kit remains required until stable Windows registration is implemented.

The published setup entry point is a renamed copy of the same inventoried apphost and defaults to setup; `Desktop.exe --setup` remains available. The embedded managed entry assembly follows the [.NET apphost design](https://github.com/dotnet/runtime/blob/main/docs/design/features/host-components.md). Preview uses a held database file and an immutable SQLite URI only when no WAL/rollback journal exists; otherwise its record count is unavailable. This avoids sidecar writes during review while retaining normal WAL-aware validation/snapshot behavior for confirmed actions. URI support and immutable read-only semantics follow [Microsoft.Data.Sqlite connection strings](https://learn.microsoft.com/dotnet/standard/data/sqlite/connection-strings) and [SQLite URI guidance](https://www.sqlite.org/uri.html). Tests compare the complete private file inventory before/after repeated reviews. Native visual/action acceptance remains open because Windows was locked during this checkpoint; no automated action was taken through the lock screen.

October 6 native maintenance follow-up: Settings stops all admitted initialization/button actions before disposing the queue, then saves the draft/defaults and swaps to a dedicated backup/restore window under the same workspace lease. A failed stop/save prevents maintenance; the partly stopped editor is kept disabled. Offline actions are serialized; review verifies a bounded local completed backup and displays its date, identity, record/file count and size. Separate restore confirmation is bound to that exact review, consumed on execution and revalidated against its manifest before replacement. Changed/partial/unbounded backups and a lost lease are refused. Backend interruption recovery settles before another action can run. Returning validates recovery/schema/defaults and constructs a new editor; the old model cannot overwrite restored state. Direct --maintenance startup checks active installed binaries/binding without requiring a healthy queue or settings, enabling retained-state repair. Confirmed native replacement, active real inference interruption, broader accessibility and actual host termination remain acceptance gates.

October 6 setup follow-up: Settings, the external maintenance `check-setup` command, and install reporting expose the same read-only bounded inspection. It checks tools/host versions and exact local context before daemon/provider inspection; the provider path verifies owned container/image/configuration and loopback health with GET only. Missing/stopped/unhealthy/loading/busy/resource/timeout observations remain distinct; raw subprocess errors and paths are withheld, and no private state/recovery allowance is written. The declared deployment baseline is Windows 11 x64 23H2 or newer, subject to edition/servicing approval. WSL 2.1.5 is checked when present, but virtualization/backend features and corporate entitlement remain externally verified. These bounds/locations reflect [Docker Windows prerequisites](https://docs.docker.com/desktop/setup/install/windows-install/) and [WSL backend guidance](https://docs.docker.com/desktop/features/wsl/); bundled .NET servicing remains tied to the release, following [.NET 10 supported operating systems](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md). User/system Docker locations share a guarded resolver so recovery can find an approved per-user installation. No new installation or privilege action is introduced.

October 6 installation follow-up: explicit offline command-line deployment uses separate per-user binary/private roots, immutable checksum-verified release folders and an atomic active-release record. A deployment journal pairs activation with the schema-compatible private snapshot, compensates before activation and resumes recorded uninstall removal after it. A rollback first preserves the current state so it can be undone. Installed desktop startup verifies ownership, package integrity, schema compatibility and its active executable; path recognition follows Windows case-insensitive semantics. Private snapshots retain frozen jobs and checked PCM bytes. No signing trust is inferred from a checksum, and no prerequisite, provider image or corporate policy is automatically changed.

Uninstall scopes are captured before commit and bounded by entry/journal limits. Unexpected paths, shapes, links, changed bytes and unknown files stop removal. Each Windows file is opened with read/delete access and read sharing only, checked through that handle, then marked for deletion through the same handle; writers/renames cannot replace the validated file in between. This follows Microsoft's [CreateFile sharing and reparse-point rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea) and [SetFileInformationByHandle deletion API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). Only empty directories are removed. A pending committed uninstall can retry remaining exact receipts; unknown root files, separate exports, models and Docker artifacts remain outside the ledger. Command-line installation is implemented; GUI setup, Windows registration/shortcuts, full prerequisite matrix, signing and fresh-machine acceptance remain open. Read-only setup diagnostics are implemented as described above.

The following decisions resolve implementation details without changing the settled product architecture. Source and script offsets use UTF-16 code units, matching WPF; chunk boundaries never divide surrogate pairs. This explicit convention differs from the document's recommended scalar-offset convention.

1. **Native desktop:** WPF on `net10.0-windows`, MVVM with async commands. Core logic targets `net10.0` independently. A per-Windows-user mutex prevents concurrent app workers. No hosted capture interface is introduced. [Microsoft WPF overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/).
2. **Durability:** Microsoft.Data.Sqlite 10.0.5, patched SQLite native bundle 3.0.5 / SQLite 3.53.4, WAL and `synchronous=FULL`. Application ID, schema version and migration history guard compatibility; legacy migrations first create a verified consistent snapshot through [Microsoft.Data.Sqlite's backup API](https://learn.microsoft.com/dotnet/standard/data/sqlite/backup). [SQLite integrity checks](https://sqlite.org/pragma.html#pragma_integrity_check) and record validation guard startup/backup. Source, script, preparation map, provider/settings snapshot, receipts, and export journal are committed with each checkpoint. Local JSON holds defaults and autosaved draft; unreadable draft data is preserved before explicit edits replace it. Local work survives app close/crash; stale in-flight stages requeue after reconciliation unless a durable cancellation request exists. Cancellation is saved before signalling active work and clears only on explicit retry or verified publication. A file lease shared with maintenance supplements the native mutex; backup/draft recovery copies remain separately retained.
3. **Engines:** Provide both CPU Kokoro ONNX 0.4.9 / Kokoro v1.0 and Piper 1.3.0 / Lessac medium for evaluation. Kokoro `af_heart` is the initial default, **not user-approved production voice**. Pin the tested image identity locally; model checksums and Python dependency versions are tracked. Engines share a versioned service contract but separate inference containers. [Kokoro ONNX](https://github.com/thewh1teagle/kokoro-onnx), [Piper Python API](https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/API_PYTHON.md).
4. **Inference contract:** `GET /health` returns CommuteCast identity, contract 1, engine, ready/loading/failed state, active counter, installed voices, and provider fingerprint. `POST /speech` accepts text, voice, 0.7–1.4 speed, and matching fingerprint; returns PCM WAV. Model files, service source, and dependency manifest contribute to fingerprint. No cloud provider or model-generated rewrite/title.
5. **Bounds:** 250,000 source characters; conservative 450-character desktop chunks; provider request cap 900; one active synthesis; readiness 120 seconds; HTTP synthesis 5 minutes; normalization 2 minutes; encode 15 minutes; decode 10 minutes. Cancellation kills owned host subprocess trees. Server-side inference may settle after a disconnected client; readiness waits for active=0 before subsequent generation rather than killing a busy container. Retry never changes an immutable job's model identity.
6. **Audio:** Canonical mono 24kHz signed 16-bit PCM; checksummed chunk receipts; single MP3 encode at 128kbps; 150ms gaps after chunk-ending sentences/paragraphs; no gaps at unpunctuated word splits. Explicit chunk/audio contract versions contribute to the receipt fingerprint; pre-version cached receipts regenerate on retry. Assembly rechecks ordered contiguous script spans, receipt ordinals, locked-file hashes and actual sample counts. Final duration tolerance 300ms accounts for encoder delay/padding. Zero/near-silent or implausibly short/long chunks block export. This is anomaly detection, not an ASR/spoken-fidelity guarantee.
7. **Publication:** Original UTC time, sanitized title, full 128-bit job ID; ID3v2.3 Unicode title, app, year, full timestamp in `commutecast_created_utc`, job identity in `commutecast_job_id` and comment. Generate privately, lock source from hash through copy, persist export intent, exclusively create a job-unique `.partial` on the destination volume, persist staging ownership, flush, verify SHA256, recheck destination/hash, rename without overwrite, persist committed state. The rename wins any cancellation arriving afterward. A matching journaled final file reconciles after a crash; known incomplete staging is recreated and unknown staging is preserved for inspection. A crash before the ownership checkpoint can therefore require manual staging inspection. Missing/moved exports retain history.
8. **Service ownership:** Exact image ID from explicit setup, local Docker pipe context, Compose project `commutecast`, ownership and contract labels, and exact loopback binding are verified before startup/inference. No install, elevation, pull, restart, or unrelated-container mutation during recovery. The existing default bridge is used because this development Docker engine has exhausted its predefined network address pools.
9. **Destination:** User chooses an existing local corporate synced folder. Write permission is tested; folder existence, separation from private storage, junction/symlink guards, and copy/hash checks are repeated at publication. No tenant, OneDrive path, Android permission, or upload verification is assumed. Selecting a different retry destination is explicit and preserves completed audio.
10. **Distribution:** Portable, self-contained Windows x64 package. Corporate code signing/MSIX/installer selection remains open pending IT deployment policy. Third-party licensing and actual voice/phone acceptance remain visible gates.
11. **Current-state maintenance:** A self-contained command-line tool shares the exclusive workspace file lease and holds the compatibility desktop mutex on its owning thread. Offline backup includes the consistent SQLite snapshot, private draft/settings/provider/recovery state and current job files, with bounded path/manifest and full checksum validation. Restore first stages and verifies incoming data, journals original per-item digests, retains previous state, then commits only after rechecking the installed files and database. Startup rolls an unfinished restore back; a committed journal keeps the restored state. Unknown, incompatible or changed recovery data is preserved for inspection. Unique exclusive atomic-write staging and bounded path-lock serialization avoid overwriting unknown temporary files or sharing them between writers. Historical copies/models/Docker/exports are excluded; this is local state recovery, not an installer rollback or provider reprovisioning. Fault-injection fixtures and observed isolated fixture-host process terminations cover restore/recovery boundaries; native desktop termination/restart, power-loss and deployment acceptance remain separate.
12. **Release integrity:** Explicit publication seals a sorted complete package inventory and records physical binary/runtime build versions, app version, architecture, schema range and provider contract. A content-derived package ID excludes creation time so resealing unchanged content remains identifiable. Verification refuses changed/missing/unlisted files, unsupported declarations, unsafe paths and known private-state artifacts. Checksums do not establish publisher authenticity/signing. Versioned install/activation, compatible state-and-artifact rollback and scoped uninstall are implemented with isolated command and reviewed-session fixtures. Stable Windows registration, native confirmed action and fresh-user/machine acceptance remain open. Atomic state replacement has a bounded Windows retry for only access/sharing/lock violations; unreleased locks fail while retaining original state.
