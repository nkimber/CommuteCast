# Implementation decisions

Date: October 5, 2026 (America/New_York).

October 6 native deployment follow-up: a dedicated WPF setup mode reuses the verified installer transactions and owns the editor's compatibility mutex without loading the queue coordinator or speech provider. Review/check actions do not create either root. A single-use review binds package identity, installation owner/state, the exact pending journal hash and a bounded private inventory; apply reacquires the private lease and rechecks each before mutation. Explicit uninstall repeats the reviewed private fingerprint check immediately before its removal journal. Pending deployment is reviewed without implicit recovery. Install validates the saved queue before activation and never resets corrupt data. Launch releases setup before starting the verified active desktop. Uninstall refuses a source kit inside the installation root; a complete external portable kit remains required until stable Windows registration is implemented.

The published setup entry point is a renamed copy of the same inventoried apphost and defaults to setup; `Desktop.exe --setup` remains available. The embedded managed entry assembly follows the [.NET apphost design](https://github.com/dotnet/runtime/blob/main/docs/design/features/host-components.md). Preview uses a held database file and an immutable SQLite URI only when no WAL/rollback journal exists; otherwise its record count is unavailable. This avoids sidecar writes during review while retaining normal WAL-aware validation/snapshot behavior for confirmed actions. URI support and immutable read-only semantics follow [Microsoft.Data.Sqlite connection strings](https://learn.microsoft.com/dotnet/standard/data/sqlite/connection-strings) and [SQLite URI guidance](https://www.sqlite.org/uri.html). Tests compare the complete private file inventory before/after repeated reviews. Native visual/action acceptance remains open because Windows was locked during this checkpoint; no automated action was taken through the lock screen.

October 6 native maintenance follow-up: Settings stops all admitted initialization/button actions before disposing the queue, then saves the draft/defaults and swaps to a dedicated backup/restore window under the same workspace lease. A failed stop/save prevents maintenance; the partly stopped editor is kept disabled. Offline actions are serialized; review verifies a bounded local completed backup and displays its date, identity, record/file count and size. Separate restore confirmation is bound to that exact review, consumed on execution and revalidated against its manifest before replacement. Changed/partial/unbounded backups and a lost lease are refused. Backend interruption recovery settles before another action can run. Returning validates recovery/schema/defaults and constructs a new editor; the old model cannot overwrite restored state. Direct --maintenance startup checks active installed binaries/binding without requiring a healthy queue or settings, enabling retained-state repair. Confirmed native replacement, active real inference interruption, broader accessibility and actual host termination remain acceptance gates.

October 6 setup follow-up: Settings, the external maintenance `check-setup` command, and install reporting expose the same read-only bounded inspection. It checks tools/host versions and exact local context before daemon/provider inspection; the provider path verifies owned container/image/configuration and loopback health with GET only. Missing/stopped/unhealthy/loading/busy/resource/timeout observations remain distinct; raw subprocess errors and paths are withheld, and no private state/recovery allowance is written. The declared deployment baseline is Windows 11 x64 23H2 or newer, subject to edition/servicing approval. WSL 2.1.5 is checked when present, but virtualization/backend features and corporate entitlement remain externally verified. These bounds/locations reflect [Docker Windows prerequisites](https://docs.docker.com/desktop/setup/install/windows-install/) and [WSL backend guidance](https://docs.docker.com/desktop/features/wsl/); bundled .NET servicing remains tied to the release, following [.NET 10 supported operating systems](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md). User/system Docker locations share a guarded resolver so recovery can find an approved per-user installation. No new installation or privilege action is introduced.

October 6 installation follow-up: explicit offline command-line deployment uses separate per-user binary/private roots, immutable checksum-verified release folders and an atomic active-release record. A deployment journal pairs activation with the schema-compatible private snapshot, compensates before activation and resumes recorded uninstall removal after it. A rollback first preserves the current state so it can be undone. Installed desktop startup verifies ownership, package integrity, schema compatibility and its active executable; path recognition follows Windows case-insensitive semantics. Private snapshots retain frozen jobs and checked PCM bytes. No signing trust is inferred from a checksum, and no prerequisite, provider image or corporate policy is automatically changed.

Uninstall scopes are captured before commit and bounded by entry/journal limits. Unexpected paths, shapes, links, changed bytes and unknown files stop removal. Each Windows file is opened with read/delete access and read sharing only, checked through that handle, then marked for deletion through the same handle; writers/renames cannot replace the validated file in between. This follows Microsoft's [CreateFile sharing and reparse-point rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea) and [SetFileInformationByHandle deletion API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). Only empty directories are removed. A pending committed uninstall can retry remaining exact receipts; unknown root files, separate exports, models and Docker artifacts remain outside the ledger. Command-line installation is implemented; GUI setup, Windows registration/shortcuts, full prerequisite matrix, signing and fresh-machine acceptance remain open. Read-only setup diagnostics are implemented as described above.

The supplied product document was still being populated at the first read; the full 25-section baseline is now available and was reviewed. The original is preserved unchanged. The following decisions resolve implementation details without changing the settled product architecture. Source and script offsets use UTF-16 code units, matching WPF; chunk boundaries never divide surrogate pairs. This explicit convention differs from the document's recommended scalar-offset convention.

1. **Native desktop:** WPF on `net10.0-windows`, MVVM with async commands. Core logic targets `net10.0` independently. A per-Windows-user mutex prevents concurrent app workers. No hosted capture interface is introduced. [Microsoft WPF overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/).
2. **Durability:** Microsoft.Data.Sqlite 10.0.5, patched SQLite native bundle 3.0.5 / SQLite 3.53.4, WAL and `synchronous=FULL`. Application ID, schema version and migration history guard compatibility; legacy migrations first create a verified consistent snapshot through [Microsoft.Data.Sqlite's backup API](https://learn.microsoft.com/dotnet/standard/data/sqlite/backup). [SQLite integrity checks](https://sqlite.org/pragma.html#pragma_integrity_check) and record validation guard startup/backup. Source, script, preparation map, provider/settings snapshot, receipts, and export journal are committed with each checkpoint. Local JSON holds defaults and autosaved draft; unreadable draft data is preserved before explicit edits replace it. Local work survives app close/crash; stale in-flight stages requeue after reconciliation unless a durable cancellation request exists. Cancellation is saved before signalling active work and clears only on explicit retry or verified publication. A file lease shared with maintenance supplements the native mutex; backup/draft recovery copies remain separately retained.
3. **Engines:** Provide both CPU Kokoro ONNX 0.4.9 / Kokoro v1.0 and Piper 1.3.0 / Lessac medium for evaluation. Kokoro `af_heart` is the initial default, **not user-approved production voice**. Pin the tested image identity locally; model checksums and Python dependency versions are tracked. Engines share a versioned service contract but separate inference containers. [Kokoro ONNX](https://github.com/thewh1teagle/kokoro-onnx), [Piper Python API](https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/API_PYTHON.md).
4. **Inference contract:** `GET /health` returns CommuteCast identity, contract 1, engine, ready/loading/failed state, active counter, installed voices, and provider fingerprint. `POST /speech` accepts text, voice, 0.7–1.4 speed, and matching fingerprint; returns PCM WAV. Model files, service source, and dependency manifest contribute to fingerprint. No cloud provider or model-generated rewrite/title.
5. **Bounds:** 250,000 source characters; conservative 450-character desktop chunks; provider request cap 900; one active synthesis; readiness 120 seconds; HTTP synthesis 5 minutes; normalization 2 minutes; encode 15 minutes; decode 10 minutes. Cancellation kills owned host subprocess trees. Server-side inference may settle after a disconnected client; readiness waits for active=0 before subsequent generation rather than killing a busy container. Retry never changes an immutable job's model identity.
6. **Audio:** Canonical mono 24kHz signed 16-bit PCM; checksummed chunk receipts; single MP3 encode at 128kbps; 150ms gaps after chunk-ending sentences/paragraphs; no gaps at unpunctuated word splits. Explicit chunk/audio contract versions contribute to the receipt fingerprint; pre-version cached receipts regenerate on retry. Assembly rechecks ordered contiguous script spans, receipt ordinals, locked-file hashes and actual sample counts. Final duration tolerance 300ms accounts for encoder delay/padding. Zero/near-silent or implausibly short/long chunks block export. This is anomaly detection, not an ASR/spoken-fidelity guarantee.
7. **Publication:** Original UTC time, sanitized title, full 128-bit job ID; ID3v2.3 Unicode title, app, year, full timestamp in `commutecast_created_utc`, job identity in `commutecast_job_id` and comment. Generate privately, lock source from hash through copy, persist export intent, exclusively create a job-unique `.partial` on the destination volume, persist staging ownership, flush, verify SHA256, recheck destination/hash, rename without overwrite, persist committed state. The rename wins any cancellation arriving afterward. A matching journaled final file reconciles after a crash; known incomplete staging is recreated and unknown staging is preserved for inspection. A crash before the ownership checkpoint can therefore require manual staging inspection. Missing/moved exports retain history.
8. **Service ownership:** Exact image ID from explicit setup, local Docker pipe context, Compose project `commutecast`, ownership and contract labels, and exact loopback binding are verified before startup/inference. No install, elevation, pull, restart, or unrelated-container mutation during recovery. The existing default bridge is used because this development Docker engine has exhausted its predefined network address pools.
9. **Destination:** User chooses an existing local corporate synced folder. Write permission is tested; folder existence, separation from private storage, junction/symlink guards, and copy/hash checks are repeated at publication. No tenant, OneDrive path, Android permission, or upload verification is assumed. Selecting a different retry destination is explicit and preserves completed audio.
10. **Distribution:** Portable, self-contained Windows x64 package. Corporate code signing/MSIX/installer selection remains open pending IT deployment policy. Third-party licensing and actual voice/phone acceptance remain visible gates.
11. **Current-state maintenance:** A self-contained command-line tool shares the exclusive workspace file lease and holds the compatibility desktop mutex on its owning thread. Offline backup includes the consistent SQLite snapshot, private draft/settings/provider/recovery state and current job files, with bounded path/manifest and full checksum validation. Restore first stages and verifies incoming data, journals original per-item digests, retains previous state, then commits only after rechecking the installed files and database. Startup rolls an unfinished restore back; a committed journal keeps the restored state. Unknown, incompatible or changed recovery data is preserved for inspection. Unique exclusive atomic-write staging and bounded path-lock serialization avoid overwriting unknown temporary files or sharing them between writers. Historical copies/models/Docker/exports are excluded; this is local state recovery, not an installer rollback or provider reprovisioning. Fault-injection fixtures emulate interruption boundaries; actual host termination and deployment acceptance remain separate.
12. **Release integrity:** Explicit publication seals a sorted complete package inventory and records physical binary/runtime build versions, app version, architecture, schema range and provider contract. A content-derived package ID excludes creation time so resealing unchanged content remains identifiable. Verification refuses changed/missing/unlisted files, unsupported declarations, unsafe paths and known private-state artifacts. Checksums do not establish publisher authenticity/signing. Versioned install/activation, compatible state-and-artifact rollback and scoped uninstall are implemented with isolated command and reviewed-session fixtures. Stable Windows registration, native confirmed action and fresh-user/machine acceptance remain open. Atomic state replacement has a bounded Windows retry for only access/sharing/lock violations; unreleased locks fail while retaining original state.
