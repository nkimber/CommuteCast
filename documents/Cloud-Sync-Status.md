# MP3 cloud sync status

Validated October 9, 2026. The desktop reads the recorded exported MP3's Windows Cloud Files metadata on a background worker when the library refreshes and every ten seconds. An explicit `CF_PLACEHOLDER_STATE_IN_SYNC` flag produces the synced check mark. A recognized placeholder without that flag is pending/not marked synced; a missing export and unavailable status remain separate states. Narration details and copied delivery information now reflect the same observation as the library icon.

Windows can disguise cloud placeholders for an application, hiding the reparse tag required by `CfGetPlaceholderStateFromAttributeTag`. The query now calls `RtlSetThreadPlaceholderCompatibilityMode(PHCM_EXPOSE_PLACEHOLDERS)` before directory enumeration and restores the exact previous mode in `finally`. No asynchronous continuation occurs within that scope, and no process-wide compatibility setting is changed. The query lives in Infrastructure so the existing test project can exercise the production implementation without loading WPF.

Only directory metadata is read: the check never opens MP3 contents, downloads online-only audio, changes pinning or provider sync state, or contacts a cloud API. It checks the MP3 rather than inferring its state from the folder, and rejects a directory substituted for the export. Invalid names, relative/UNC destinations, uncommitted/deleting jobs, unsupported APIs and failed metadata queries retain an unavailable result. The reported state is the local Windows/provider observation; phone playback and independent remote-account availability remain separate acceptance.

Microsoft documents [the placeholder-state query](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetplaceholderstatefromattributetag), [thread compatibility mode and hidden metadata](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-rtlsetthreadplaceholdercompatibilitymode), and [OneDrive availability icons](https://support.microsoft.com/en-us/onedrive/what-do-the-onedrive-icons-mean). Local availability/pinning alone does not substitute for the explicit in-sync flag.

Validation:

- `dotnet test tests\CommuteCast.Tests\CommuteCast.Tests.csproj -c Release --artifacts-path artifacts\cloud-sync-build --no-restore --filter FullyQualifiedName~CloudFileSyncTests --logger "trx;LogFileName=cloud-sync-focused-isolated.trx"`: **17 passed, zero failed/skipped**. Cases cover actual isolated registered Windows cloud placeholders with and without the in-sync flag, Unicode names, thread-mode restoration, online-only content remaining unhydrated without a connected provider, ordinary files, missing exports, directories and invalid export inputs. Earlier synthetic-provider attempts failed because the fixture requested on-demand directory population without a connected provider; the final fixture uses the documented ALWAYS_FULL population policy.
- A retained local .NET probe compares the original and updated production implementations against three existing OneDrive MP3s. For all three, the original returns `Unknown` under application-default and explicitly disguised modes; the updated implementation returns `InSync`. Both return `InSync` under explicitly exposed mode. Each of the nine updated queries restores its prior thread mode. The source-free observations are in ignored `artifacts/cloud-sync-os-probe.json`; paths and file contents are excluded from that report.
- `dotnet build CommuteCast.sln -c Release --artifacts-path artifacts\cloud-sync-solution-build`: **all eight projects build, zero warnings/errors**. Isolated outputs avoid competing with another test run using the normal Release directory. The shared working tree contained unrelated MP3-comment work during validation; that work is outside this increment.

The complete regression suite and live WPF refresh/restart were not executed for this increment. The currently running desktop must be rebuilt and restarted to load the change. Existing native acceptance assumptions do not add new observed UI evidence.
