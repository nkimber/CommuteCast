# Remote narration through OneDrive

CommuteCast exchanges private narration requests, status, and finished MP3s through a folder synced by the Windows OneDrive client. Set up a dedicated folder that both computers are allowed to access. It will contain the submitted text. The work laptop can submit from the Windows app using its existing sync client, and Android can open the `Ready to Listen` folder in OneDrive.

Choose the shared queue root explicitly on each Windows PC. For example, select `CommuteCast` under the OneDrive account approved for the material you will submit. Worker MP3s go to its `Ready to Listen` subfolder. Choose the desktop's normal MP3 output folder separately in **Settings → Delivery**. Earlier desktop releases could select a personal folder automatically. If an older saved shared folder matches that default, review the displayed account path and choose **Save remote settings** before sending new requests. Open **Admin** to see the effective paths for requests, status, staging, MP3s, and local data.

1. On the basement PC, set up CommuteCast with working speech providers and FFmpeg. Open **Settings → Remote queue**, choose the local copy of the shared folder, enable **Let this PC generate remote jobs**, and name the worker. Keep the app running. The worker opens automatically when CommuteCast starts with these settings.
2. If you want automatic substitutes, audition and save narration presets on the worker. Enter their names in preference order, one per line, in the remote settings. Remote work uses local speech by default. Enable hosted speech only for a worker allowed to send submitted text to its configured provider.
3. On the work laptop, open the remote settings and choose its local copy of the same folder. Leave remote generation off on that laptop. In **New narration**, paste the text and choose the voice and pace. Select **Send to a remote worker**, choose a machine from the roster, and send. CommuteCast can queue a request for a registered worker that is asleep or offline.
4. Open **Remote queue** from **Your library** to see waiting, active, uploading, ready, and attention states. A finished narration with a substitute shows **Ready · fallback used**. Select it to see the requested and actual settings. Use **Copy speech diagnostics** to hand the job ID, settings, and repair guidance to Codex. The diagnostic summary omits the narration text.

`Inbox` holds immutable requests. Each request targets one worker ID, so machines sharing the folder have separate assignments. `Workers` holds one roster entry per registered worker, normally refreshed once a minute. The desktop shows check-ins older than four minutes as offline and preserves explicit stopped and disabled states. `Status` holds the latest snapshot per job. Windows sync can delay either kind of update. Temporary files go into `Staging` while `Ready to Listen` holds the finished MP3s. The worker reports **Ready** when Windows reports the finished file in sync. Use OneDrive Files On-Demand on the worker so Windows exposes that status. After ten minutes without confirmation, the row stays **Uploading** and tells you what to check in OneDrive.

The worker uses the existing serial local queue and saves the actual speech settings before rendering. On restart it reuses saved, validated chunks. Finished audio is kept locally, so interrupted delivery can retry with the same output name. The worker saves confirmed delivery in its local queue. If you later remove the listening copy, the worker shows it as missing and keeps the private audio available for recovery. After fixing a missing voice, open the affected narration in **Remote queue** on the worker and choose **Retry on this worker**. The same job ID and source are reused. A hosted request interrupted after it may have been billed follows the existing explicit retry policy. A job assigned to a missing machine stays assigned until that worker returns.

On Windows, test first with CommuteCast and OneDrive running under the signed-in worker account. From the extracted portable package, run `.\scripts\Register-CommuteCast-Worker.ps1 -Executable .\app\CommuteCast.Desktop.exe` under that account to launch CommuteCast at sign-in. For an installed copy, pass its stable `CommuteCast.exe` path instead. Add `-WhatIf` to preview the change or run the script with `-Remove` to remove the sign-in task. If the shared folder appears after CommuteCast starts, the app retries opening it. Recovery before sign-in depends on the host setup, including availability of OneDrive and any local speech runtime.

## Send from Android

The optional web host lets you send pasted text from Chrome and follow the same remote job list. Run it under an account with access to the shared OneDrive folder and give it its own private workspace. Set `RemoteQueue__Folder` to the absolute local path of that folder on the web host. Set `RemoteQueue__ListeningFolderUrl` if you want a link to the `Ready to Listen` folder in OneDrive. Use an HTTPS link that keeps your intended Microsoft account permissions.

Open `/listen` in Chrome and use **Send a narration**, or go directly to `/remote`. Use the approved [web sign-in setup](Web-Application.md) for access away from home. The form offers Studio defaults and saved presets. Select a worker and a preset, enter the text, and send it. The browser request uses the worker's existing serial queue. Chrome can open both pages within the CommuteCast home-screen app.

## Check both copies of the shared folder

From the portable package, run `.\app\CommuteCast.Maintenance.exe inspect-remote --folder "<local copy of the shared folder>"` on each PC. Compare the worker IDs and check-in times. Add `--job <job ID>` to compare one request, its status, and its output metadata. The job ID is available under **Copy speech diagnostics** for a job that needs attention, or as the name of its request file in `Inbox`.

The report only reads the roster, status, and file metadata. It excludes the request contents, worker names, titles, and local paths. `RegisteredCloudFilesRoot` means Windows recognizes a local sync provider for that path. Compare the worker and job IDs to verify that the two PCs actually share the same folder. [Windows sync root metadata](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetsyncrootinfobypath)

For live acceptance, use a short synthetic script, close the work app after submission, and verify that the remote status advances when you reopen it. Check that the actual Android OneDrive account can open the completed MP3. Send a second narration from Chrome on Android and check that the same worker picks it up. Repeat with the basement app restarted after the first chunk and with a requested voice missing from its catalog. Check for one delivered file with the expected fallback notice. The automated restart test uses simulated speech, real FFmpeg, and a temporary Windows Cloud Files sync root. It exercises Windows in-sync metadata without connecting to an actual OneDrive account. [Windows Cloud Files confirmation](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfconverttoplaceholder)

The automated batch test submits four requests through the desktop file protocol and the phone API, checks their rendering order and lack of overlap, and verifies four completed MP3s. It uses real FFmpeg with simulated speech and sync confirmation. The phone form was also exercised in Chrome at a 390-pixel viewport with an isolated queue.

To exercise the installed speech provider with the remote worker, run `dotnet run --project tools/CommuteCast.Pilot -c Release -- --verify-remote-worker kokoro` from the repository, or select `piper`. The command requires a provisioned, ready, idle engine. It runs two synthetic jobs in a fresh local folder under `artifacts/pilot`, checks serial rendering and missing-voice fallback, and verifies each MP3 against its saved hash. The local pilot leaves delivery at **Uploading** because the folder has no OneDrive confirmation. The report and listening samples stay in the pilot folder.

The local pilot passed with both installed providers. Kokoro Heart produced MP3s of 9.08 and 8.28 seconds. Piper lessac-medium produced MP3s of 7.29 and 6.82 seconds. Each pair rendered in submission order and the second request in each pair reported a fallback. The two-device OneDrive and Android acceptance runs remain open.

To exercise an unexpected worker exit, run `dotnet run --project tools/CommuteCast.Pilot -c Release -- --verify-remote-worker-loss piper` or choose `kokoro`. The pilot terminates its isolated worker process during the second chunk after verifying that the first chunk and its receipt are saved. The restarted worker reuses the first chunk and the selected fallback, completes the interrupted request, and processes the waiting request next. The speech service keeps running throughout the test. The test records two validated local MP3s and leaves proof of cloud delivery to the live OneDrive pilot.

The interruption pilot passed with Piper and Kokoro. Each worker recovered automatically, preserved the first chunk and fallback choice, and produced exactly two MP3s in the original queue order. This test covers loss of the worker process during real speech generation. A full Windows reboot and access from the actual work laptop and Android phone remain checks for the live pilot.
